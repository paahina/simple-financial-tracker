1. Debt Management
======================================================================

### 1.1. Add Debt Categories
**Priority:** High | **Status:** [x] One category per debt; create uses a single amount + label

**Scope:** Individual debts only. Contribution debts (1.2) do not use category
lines.

**Objective:** Categorize what is owed and track payments per category with
separate due dates.

**Requirements:**
- Create or select a category when adding or managing an individual debt.
- Predefined categories and/or custom categories (see open decisions).
- Display categories under the debt record.
- Each category line: label, original amount, due date, paid, remaining.
- Overall debt owed = sum of category remaining (or equivalent rules).
- Extend current Debt + DebtPayment workflow; do not replace it.
- Payments must update the correct category balance (allocation TBD in open
  decisions).

**Example:**

Total debt ₱10,000:
- Food: ₱3,000, due Oct 25
- Rent: ₱5,000, due Oct 30
- Utilities: ₱2,000, due Nov 5

**Acceptance criteria:**
- CRUD category lines on individual debts.
- Independent due dates per line.
- Payments reduce the correct line; totals stay consistent.
- Existing individual debts and payments keep working (lazy backfill if needed).

**Notes vs today:** Debt has originalAmount, additions (extra owed lines without
per-line due/paid), and payments at debt level only — extend or replace
additions pattern as needed for 1.1.

---

### 1.2. Contribution (shared debt / ambagan)
**Priority:** High | **Status:** [x] Implemented (create toggle, payers, per-payer payments)

**UI label:** **Contribution** (not “Ambagan” in the interface).

**Objective:** One shared receivable with multiple participants, each with a
fixed share and independent payment tracking.

**Model (agreed):**
- Same Debt entity with a **kind**: Individual (default) vs **Contribution**.
- Extend existing Debts UI; distinguish Contribution in list and detail.
- **No** 1.1 category lines on Contribution debts (participants only).

**Requirements:**
- Add participants by name; each has an expected share (centavos).
- **Validation:** sum of participant shares must equal debt total.
- Per participant: paid amount, remaining, status (unpaid / partial / paid).
- Record payments **per participant** (does not change other participants).
- Show total expected, total collected, remaining.
- Payment behavior matches current debt payments: money into **account** (+ pocket
  when account has sub-balances); optional **record as income** checkbox.
- **Cap:** a participant payment cannot exceed that participant’s remaining share.

**Example:**

₱3,000 shared; Juan ₱1,000 paid; Maria ₱500 of ₱1,000; Pedro ₱0 of ₱1,000.
Collected ₱1,500; remaining ₱1,500.

**Acceptance criteria:**
- CRUD participants on Contribution debts.
- Per-participant payments and caps.
- Contribution vs Individual visible in UI.
- No duplicate cash counting (same rules as linked income on debt payments).

### 3.2. To-Buy list (v1 — minimal)
**Priority:** Medium | **Status:** [x] Implemented (CRUD, Done → Shopping expense, hard delete)

**Objective:** Plan purchases; completing an item records a real expense and
removes the row.

**Persistence:** Items stored in the database (not ephemeral).

**v1 fields:**
- Item name (also used as expense label when done)
- Quantity, estimated unit price (centavos)
- Optional notes
- **No** purchase budget in v1
- Show line estimate (qty × unit price) and list estimated total

**Delete:**
- Hard delete with confirmation.
- Does **not** create a transaction.

**Done (per item):**
- Button opens confirmation dialog (like transaction create, simplified):
  - **Account** (required)
  - **Deduct from** sub-balance when account has pockets (same as transactions)
  - **Amount** (required, starts **empty** — user enters actual paid amount)
- On confirm: create **EXPENSE** with label = item name; category **Shopping**
  (falls back to the first active expense category if Shopping is missing).
- Then **hard delete** the to-buy item (no “purchased” archive in v1).

**Acceptance criteria:**
- CRUD active list items; estimates recalc on edit.
- Done → expense + item removed from DB.
- Delete → item removed, no expense.
- Account/pocket balances update once; invalidate accounts/transactions/dashboard.

4. General implementation guidelines
======================================================================

1. Inspect codebase first (models, finance.js, controllers, pages, tests).
2. Extend working features; avoid destructive schema changes.
3. Amounts in centavos; validate payments and caps.
4. Prevent duplicate accounting (linked income, pocket deltas once).
5. Match existing UI patterns (FormModal, ConfirmProvider, invalidateFamilies).
6. Add/update server tests for new money paths.
7. Implement one backlog section at a time per agreed order.

**Core principle:** Available cash, receivables, unpaid salary, and personal
liabilities stay separate. Future money is not spendable cash.
