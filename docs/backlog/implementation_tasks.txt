### 2.1. Debts page — receivable vs payable (two directions)
**Priority:** High | **Status:** [x]

**Objective:** One Debts page with two top-level tabs:
- **Tab A — Others owe you** (today’s default receivable list).
- **Tab B — You owe others** (liabilities), same debt kinds and status workflow.

**Model / API (agreed):**
- Add a **direction** (or equivalent) on Debt: `RECEIVABLE` | `PAYABLE` (default RECEIVABLE for
  existing rows — lazy backfill/migration in code).
- **Kinds on both tabs:** `INDIVIDUAL` and `CONTRIBUTION` (same as today).
- List/filter APIs accept direction + status; counts per status respect direction.
- Paged list may include **`directionTotals`** (`RECEIVABLE` / `PAYABLE` debt counts) for future use;
  **UI must not show these on the direction tabs** (see UI refinement).
- **Receivable payments:** unchanged — money **into** account (+ pocket); optional record as income.
- **Payable payments:** mirror — money **out of** account (+ pocket); optional linked **EXPENSE**
  (same anti-double-count pattern as receivable income link).
- Contribution payable: per-participant pay-down with caps; paying reduces user’s obligation to
  that participant’s share.

**UI:**
- Top tabs: **“Owed to you”** | **“You owe”** (exact labels match app tone).
- **Each** top tab has the **same four status tabs:** Pending, Partially paid, Paid, Overdue
  (reuse current status chips/filters; **status tabs keep per-status counts**).
- Create debt: direction follows active top tab (or explicit toggle on create form).
- Detail/edit/payment/add-balance flows work for both directions with correct cash sign.

**UI refinement — direction tabs (agreed):**
- Top-level direction tabs show **labels only** — **no** total debt count, parentheses, or badges
  (e.g. not “Owed to you (3)”).
- **Do not remove** status-tab counts (Pending 2, etc.).
- **Do not remove** `directionTotals` from the API; client ignores it for direction tab labels.

**Acceptance criteria:**
- Existing receivable debts unchanged after migration.
- Payable CRUD, payments, and status transitions correct; account balances update once.
- No duplicate cash with optional linked transaction on payable payments.
- Server tests for payable payment path and list filters by direction + status.
- Direction tabs read as plain “Owed to you” / “You owe”; status row still shows counts.

### 2.2. Transactions & Transfers — day panel layout and totals
**Priority:** High | **Status:** [x]

**Objective:** When a day is selected on Transactions and Transfers pages, the **right panel** layout:

1. Date heading (unchanged formatting).
2. **New transaction** / **New transfer** button — **below** date, **above** totals, **right-aligned**
   (full width row, `justify-end`).
3. **Two summary cards** for the selected day (see **UI refinement** below) — not small chips on the
   right panel.
4. Entry list and pager below.

**UI refinement — right panel only (agreed):**
- Replace `DayAmountSummary` **chips** on the **right panel** with **two large cards**, same pattern as
  Dashboard summary tiles:
  - `article` with `rounded-lg border border-neutral-200 bg-neutral-0 p-4`
  - Label: `text-sm text-neutral-500`
  - Amount: `Money` at `text-xl font-semibold` (respects navbar **hide amounts**)
- **Layout:** two cards **side by side** (`grid grid-cols-2 gap-4` or `sm:grid-cols-2`).
- **Always show both cards** for the selected day, including **₱0.00** when that side has no total
  (do not hide zero cards on the right panel).
- **Labels (page-specific):**
  - **Transactions:** **Added** | **Deducted**
  - **Transfers:** **Money in** | **Money out**
- **UX tone:** distinguish in vs out — e.g. success/green styling on the “in/added” amount, destructive/red
  on the “out/deducted” amount (card chrome stays Dashboard-neutral; accent on amount or subtle border).
- **Left day list (`DayGroupList`):** keep **compact chips** for scanability (unchanged).

**Day total rules — Transactions:**
- **Added** = sum of `INCOME` amounts on that calendar day (user timezone, same as day grouping).
- **Deducted** = sum of `EXPENSE` amounts on that day.

**Day total rules — Transfers (agreed):**
- **Added / Money in:** other → your account only (`fromAccountId` null, `toAccountId` set).
- **Deducted / Money out:** your account → other only (`fromAccountId` set, `toAccountId` null).
- **Internal** account ↔ account (including pockets): **0** on both sides (not counted).

**Implementation notes:**
- Right-panel values from `selectedDay.addedAmount` / `deductedAmount` on the days API (full day, not
  entry page slice).
- Refactor or extend `DayAmountSummary` (e.g. `variant="chips" | "cards"`, label props) to avoid
  duplicating Dashboard markup.
- Left sidebar chips must stay consistent with the same API totals.

**Acceptance criteria:**
- Right panel shows two Dashboard-style cards with correct labels per page; zeros visible.
- Hide amounts masks both card amounts; labels remain visible.
- Transfer internal-only days: both cards show 0; external in/out match server rules.
- Sidebar chips unchanged; totals match cards for the selected date.

**Definition of done for 2.2 (full):** Mark `[x]` when cards + existing layout/total rules pass QA.

### 2.3. Select dropdown — overlay; ignore parent width bounds
**Priority:** Medium | **Status:** [x]

**Problem (agreed):**
- Menu is **clipped** by narrow parents (table cells, `overflow-x-hidden` form/modal wrappers) even
  though the list is portaled — options are not fully visible.
- Earlier goal still applies: opening Select must **not** add a horizontal scrollbar on the form/page.

**Scope:** Shared **`Select`** component everywhere (all pages).

**Requirements:**
- List renders in a **portal** (e.g. `document.body`) so it is **not** clipped by parent
  `overflow: hidden/auto` or table cell width.
- **Width:** `max(trigger width, content width for longest option label)` — menu may be **wider**
  than the trigger when labels are long (e.g. account name + balance in table columns).
- **Horizontal position:** **Left edge aligned with the trigger**; if the menu would extend past the
  viewport right edge, **shift left** so it stays on screen (do not shrink below min width unless
  viewport forces `max-width` with wrapping).
- **Vertical:** keep flip above/below when near viewport edge; max height + scroll unchanged.
- **z-index** above FormModal and form content; Escape and click-outside unchanged.
- Parent layout must **not** grow or scroll horizontally when the menu opens (menu width is visual
  only, not document flow).

**Implementation notes:**
- Measure option label widths (hidden probe or canvas) or use `minWidth: triggerWidth` +
  `width: max-content` with viewport cap.
- Do **not** tie list width solely to `getBoundingClientRect().width` of the trigger when that
  causes clipped/truncated options.

**Acceptance criteria:**
- Transaction/transfer create on desktop: open Account/Category in a **narrow table column** — full
  option labels visible; menu not cut off by modal border.
- Menu at least as wide as trigger; wider when labels require it.
- No horizontal scrollbar on form/modal when menu is open.
- Other Select usages (accounts, categories, debts) behave the same.

**Definition of done for 2.3:** Mark `[x]` again only when clipping + width rules above pass QA.

### 2.4. Transaction & transfer create — desktop table row alignment
**Priority:** Medium | **Status:** [x]

**Problem (agreed):**
- On **lg+** bulk-create tables, **Account** and **Sub-balance** cells show a **subtitle** above the
  control (balance hint text). **Type**, **Category**, **Label**, **Amount**, and **Remove** do not,
  so controls sit higher and rows look misaligned.
- **`align-middle`** on the row does not fix this and can make multi-line **From/To** transfer cells
  look worse. Alignment should be **top-based** with a consistent first-line offset.
- **Transfer create (additional):** When **From other** or **To other** is selected, **Sender** /
  **Recipient** text inputs appear **without** the invisible subtitle line that sub-balance **Select**
  rows use, so those inputs sit higher than the equivalent stacked control in the opposite column.

**Scope:** Desktop table layout only on:
- `TransactionCreatePage` (multi-entry table)
- `TransferCreatePage` (multi-entry table)

Not in scope: mobile card carousel, single-row edit forms (`TransactionEditPage`, `TransferEditPage`).

**Requirements (base — shipped):**
- Table body rows: **`align-top`** (not **`align-middle`**).
- Reuse **`TableSubtitleSpacer`** (invisible `text-xs` line, `aria-hidden`) above controls that must
  align with Account/Sub-balance **Select** tops.
- **Transaction create:** spacers on Type, Category, Label, Amount, Remove; spacer + “—” when no
  sub-balance pockets.
- **Transfer create:** spacers on **Amount** and **Remove** (with `mb-2` where From/To use `space-y-2`).

**Requirements (refinement — pending):**
- **Transfer create desktop table only**, inside **From** / **To** cells:
  - When **`fromAccountId === 'other'`:** add **`TableSubtitleSpacer`** (same pattern as sub-balance
    subtitle — invisible line **directly above** the **Sender** input) before the Sender field.
  - When **`toAccountId === 'other'`:** same **directly above** the **Recipient** input.
  - Do **not** add spacers to mobile card fields; do **not** change Sender/Recipient placeholders or validation.
- Goal: Sender/Recipient inputs **line up vertically** with sub-balance **Select** stacks in the same
  row (same offset as visible/invisible subtitle + control pattern).

**Acceptance criteria:**
- Desktop transaction create: primary controls in a row share the same vertical start (unchanged).
- Desktop transfer create: Amount aligns with From account Select (unchanged).
- Desktop transfer create with **From other** + account on To (or mirror): Sender and Recipient inputs
  are not visually “jumped up” vs sub-balance selects on the other side.
- Row alignment remains **top**; errors still below controls.

**Definition of done for 2.4:** Mark `[x]` again when base + transfer “other” spacer QA pass.

### 2.5. Confirmation before save (all writes except delete)
**Priority:** Medium | **Status:** [x]

**Scope (agreed):** Every **save/submit** that persists data, **except** actions that already use
**delete** confirmation (delete keeps its own dialog).

**Includes (non-exhaustive):** transaction create/edit, transfer create/edit, account create/edit,
debt create/edit, debt payment, debt balance add, to-buy create/edit, to-buy Done → expense,
category create/edit, user profile save — any `POST`/`PUT`/`PATCH` from a form primary action.

**Requirements:**
- Use existing `ConfirmProvider` / `useConfirm` pattern (title, message, confirm/cancel).
- Submit runs only after user confirms; cancel returns to form with data intact.
- Delete/deactivate flows: **do not** add a second confirm on top of existing delete confirm.

**Acceptance criteria:**
- Spot-check each major form once; no silent saves on primary button.
- Double confirm does not appear on delete.

3. General implementation guidelines
======================================================================

1. Inspect codebase first (models, finance.js, controllers, pages, tests).
2. Extend working features; avoid destructive schema changes; backfill defaults for new enums.
3. Amounts in centavos; validate payments and caps.
4. Prevent duplicate accounting (linked income/expense, pocket deltas once).
5. Match existing UI (FormModal, ConfirmProvider, Tabs, invalidateFamilies, Toast errors).
6. Add/update server tests for new money paths and aggregates.
7. Implement one backlog section at a time per agreed v2 order.

**Core principle:** Available cash, receivables, and payables stay conceptually separate;
future/owed money is not spendable cash unless product rules say otherwise.

======================================================================

- UI workflow complete with loading/empty/error states.
- Data persists across refresh.
- Calculations and summaries correct (including day totals and direction-specific debt payments).
- Tests pass; existing flows still work.
